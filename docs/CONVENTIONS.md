# 개발 컨벤션

두 명의 개발자와 AI가 같은 판단 기준을 사용하기 위한 초기 합의안이다.
규칙 변경은 PR에서 이유를 적고 함께 합의한다. 기존 코드 전체를 한 번에 규칙에 맞추지 않는다.

## Swift

- 들여쓰기 4칸. 타입·프로토콜은 UpperCamelCase, 함수·프로퍼티는 lowerCamelCase.
- 새로운 화면은 `DiaryListView`, 화면 상태는 `DiaryListViewModel`처럼 책임을 드러낸다.
- Bool은 `isDeleted`, `hasImages`, `canSave`처럼 읽히게 작성한다.
- 기본은 `let`, 접근 범위는 필요한 만큼만 연다. 구현 상속이 필요 없는 클래스는 `final`을 쓴다.
- 함수는 한 가지 책임을 맡긴다. 파일 길이만 줄이려고 의미 없는 타입을 만들지 않는다.
- force unwrap, `try!`, 실패를 감추는 `try?`를 새로 추가하지 않는다. 오류는 호출자가 처리할 수 있게 전달한다.
- 사용자에게 보여 줄 문구와 로그용 메시지를 구분한다. 일기 본문·사진 위치·토큰을 로그에 남기지 않는다.
- 주석은 코드가 설명하지 못하는 이유·제약에 쓴다. 번역 주석과 임시 디버그 출력을 남기지 않는다.

## 상태와 비동기 처리

- 새 비동기 경계는 async/await를 우선한다. 기존 callback은 경계에서 점진적으로 감싼다.
- continuation은 정확히 한 번 완료한다. 성공·실패·취소 경로를 검증한다.
- UI 상태 변경은 `@MainActor`에서 처리한다. 네트워크/파일 작업을 동기적으로 main thread에 올리지 않는다.
- Firestore listener의 소유자와 해제 시점을 정하고, 재진입·로그아웃 시 중복 구독을 막는다.
- 로딩·내용·빈 상태·오류를 구분한다. 오류를 빈 목록으로 바꾸지 않는다.
- 저장 중 중복 제출, 사진 업로드 일부 실패, 화면 이탈 시 취소를 명시적으로 다룬다.

## 데이터·시간

- 기존 `users/{uid}/diaries/{id}`와 필드명을 무단 변경하지 않는다.
- Swift 모델 개선과 Firebase 스키마 변경은 별개 작업이다. DTO 변환으로 연결한다.
- 날짜 판단에는 명시적인 Calendar/TimeZone을 전달한다. 현재 시각이 필요하면 주입한다.
- 잘못된 날짜를 무조건 오늘로 대체하는 현재 동작은 별도 테스트와 합의 후 수정한다.
- 월간 진행도는 페이지에 로드된 일부 일기만으로 계산하지 않는다.
- 새 마을의 보상/저장 규칙은 후속 논의에서 정한다. 현재 리팩토링에 임의로 추가하지 않는다.

## 구조: 필요할 때 순차적으로 생성

```text
EveryDiary/EveryDiary/
  Domain/           # UIKit·Firebase에 독립적인 모델, 정책, use case
  Data/             # 저장 DTO, Repository 구현, Firebase adapter
  Features/         # 최종 SwiftUI 화면과 화면 상태
  Shared/           # 사용처가 확인된 날짜·설정·작은 공통 함수
  DesignSystem/     # 공통 토큰은 먼저, UI 컴포넌트는 화면 전환 때
```

현재 폴더를 미리 전부 옮기지 않는다. 로직이 분리된 기능부터 위 구조를 적용한다.
파일 이동만 하는 PR은 행동 변경 PR과 분리한다. 기능이 요구하지 않는 범용 Coordinator,
대형 DI 프레임워크, TCA 등 추가 프레임워크 도입은 별도 논의한다.

## 공통 기반과 SwiftUI

- [전환 준비 문서](UIKIT_SWIFTUI_MIGRATION.md)의 기존 자산/도구 분류를 먼저 확인한다.
- 색상은 역할별 토큰으로 이름을 정하고 같은 colorset을 양쪽 UI에서 사용한다.
- 타이포·여백·모서리 기준은 목업에서 합의한다. 임의의 숫자를 각 화면에서 복제하지 않는다.
- 날짜 저장 형식과 사용자 표시 형식은 분리한다. 공통 함수는 실제 사용처와 테스트를 근거로 추출한다.
- SwiftUI 로컬 상태는 State/Binding, 공유 참조 상태는 iOS 17의 Observation을 우선 검토한다.
  화면마다 ViewModel을 강제로 만들지 않고, 복잡한 동작/공유 상태에 필요할 때 둔다.
- UIKit 연결 adapter는 필요한 기능에 한정하고 제거 조건을 적는다.
- 디자인 토큰 구현과 전체 화면 교체는 별도 단계다. 빈 폴더나 미사용 공통 컴포넌트를 양산하지 않는다.

## Git과 PR

- 기본 통합 브랜치는 `dev`. 일반 작업은 짧은 기능 브랜치와 PR로 합친다.
- 브랜치 예: `refactor/diary-repository`, `test/diary-date`, `feat/village-policy`.
  AI 기본 접두사가 필요한 도구는 `codex/diary-repository`를 사용해도 된다.
- 커밋은 기존 형식 유지: `[Refactor] 일기 조회 책임 분리`, `[Test] 월 경계 회귀 테스트`.
  사용 태그: Init, Feat, Fix, Refactor, Test, Docs, Chore.
- PR 하나는 하나의 검토 가능한 목적. 동작 보존 리팩토링과 새로운 보상 규칙을 섞지 않는다.
- 두 개발자 중 작성자 외 한 명이 리뷰한다. AI 검토는 동료 리뷰를 보조한다.
- `Logic tests`, `Simulator build` 성공 및 해당 기능 검증 후 병합한다.
- 이 문서의 병합 기준은 팀 운영 규칙이다. GitHub branch protection을 자동 설정하지는 않는다.
- 공통 파일(`DataModel.swift`, 프로젝트 파일, 앱 진입점)은 먼저 담당을 공유하고 변경을 작게 유지한다.

## 테스트

- 이름은 `test<상황><기대결과>`로 쓴다. 구현 내부 호출 횟수보다 사용자 관점의 결과를 검증한다.
- 순수 로직은 fake 저장소·고정 시각으로 테스트한다. 운영 계정과 인터넷에 의존하지 않는다.
- 날짜·삭제/복원·데이터 호환·중복 저장처럼 리팩토링 위험이 큰 경계를 우선한다.
- 초기 CI는 XCTest를 사용한다. 테스트 프레임워크 전환은 현재 리팩토링에 섞지 않는다.
- 현재 Swift language mode는 5, 배포 대상은 iOS 17. Swift 6 모드 전환은 별도 검토한다.
