# 프로필 이미지 편집·에셋 검토 자료

2026-09-29 확인. 목표 범위는 **기본 아바타 선택 + 사용자의 앨범 사진 업로드**다. 이 문서는 현재 구현 확인과 다음 구현·에셋 선택을 위한 자료이며, 아래 외부 그림을 앱에 추가했다는 뜻은 아니다.

## 현재 구현

- `codex/login-flow`의 설정 프로필 카드를 누르면 SwiftUI 편집 화면에서 닉네임과 아바타를 함께 고른다. 현재 아바타는 흰 `person.fill`과 단색 원형 배경 8종(보라·바이올렛·라벤더·초록·파랑·주황·갈색·분홍)이다. 설정 목업의 보라색 사람 아이콘과 방향이 맞다.
- 선택값은 Firebase Auth의 `photoURL`에 `harudiary-avatar://purple` 같은 문자열로 저장한다. 일기 문서나 Firebase Storage에는 쓰지 않는다. 저장 직후 화면 상태는 갱신되지만, 실제 Firebase 저장·앱 재시작 후 유지·다른 기기 동기화는 별도 실사용 확인이 필요하다.
- **현재의 ‘이미지 편집’은 제공된 8종 중 선택이다.** 앨범 사진 업로드와 자르기는 아직 구현돼 있지 않다. 사진 업로드는 이번 목표에 포함된다. 카메라 촬영과 자르기 UI는 별도 결정 사항이다.
- 이전 로컬 구현은 `moon`·`sparkles`·`leaf`·`cloud`·`sun`·`book`·`cup`·`heart`를 저장했다. 지금 코드는 이 값을 읽지 못해 기본 보라로 표시한다. 이미 테스트 계정에 저장된 값이 있다면 배포 전 **기존 값을 읽는 호환 매핑**을 추가하고 테스트한다. 새 에셋을 붙일 때도 저장 ID를 그림 파일 이름과 분리해, 디자인만 바꿔도 계정 선택이 유지되게 한다.

## 팀에 권하는 방향

현재의 색상 선택은 목업과 가장 가깝고, 용량·서버·라이선스 부담이 없다. 이 방향을 기본으로 두되, ‘프로필마다 다른 느낌’을 원한다면 **동일한 원형 배경 규칙에 작은 일러스트 8종**을 얹는 안을 먼저 비교한다. 이미 저장한 아바타 ID는 유지하고 `ProfileAvatarView`의 그림만 바꾸면 된다. 외부 라이브러리를 런타임에 추가하거나 원격 아바타 API에 의존할 필요는 없다.

사진 업로드는 이 아바타 선택과 나란히 제공한다. 편집 화면에서 ‘기본 아바타’와 ‘내 사진’을 분명히 구분하고, 사진을 고른 뒤에는 업로드 전에 미리보기를 보여준다. 저장 중에는 중복 탭을 막고, 실패하면 기존 프로필을 그대로 유지하며 재시도할 수 있게 한다.

편집 화면 시안은 현재 큰 원형 미리보기 아래에 `앨범에서 사진 선택` 버튼을 두고, 그 밑에 기본 아바타 8종을 놓는 구성이 적합하다. 사진을 고르면 큰 원형 미리보기에 바로 반영하되 실제 업로드는 `저장`에서 시작한다. 저장 중에는 진행 상태를 표시하고, 실패하면 편집 화면을 닫지 않는다. 앨범을 열었다가 취소해도 닉네임과 아바타 선택은 유지한다.

| 안 | 인상·장점 | 적용 시 주의 |
|---|---|---|
| 현재 단색 사람 아이콘 | 목업과 일치, 가장 단정함, 추가 자산 없음 | 8개가 색만 달라 개성이 약함. 흰 그림과 연한 배경의 대비 확인 |
| 자체 제작 ‘하루의 작은 친구’ 8종 | 앱만의 정체성, 온보딩·일기 분위기와 연결 | 그림을 같은 굵기·크기·명암으로 8개 모두 제작·검수해야 함 |
| [DiceBear Moods](https://www.dicebear.com/styles/moods/) | 부드러운 파스텔과 간단한 표정, 일기 앱에 가장 자연스러운 무료 후보 | 생성 결과 8개를 고정 자산으로 수출하고, 현재 목업과 함께 비교 |
| [DiceBear Critters](https://www.dicebear.com/styles/critters/) | 둥글고 귀여운 동물·괴물형 캐릭터, 선택 재미가 큼 | 분위기가 어린이 앱처럼 보일 수 있어 설정 화면 50pt에서 확인 |
| [DiceBear Lorelei](https://www.dicebear.com/styles/lorelei/) | 다양한 인물 표현, ‘내 프로필’의 개성이 큼 | 선이 세밀해 현재 50pt 프로필 카드에서 흐려질 수 있음 |

### 자체 제작 시 8종 초안

색상만 바뀌는 현재 상태를 유지하면서 점진적으로 교체할 수 있도록, 아래 주제와 색상을 **제안**한다. 그림 주제와 출시 여부는 목업 비교 후 정한다. 각 그림은 한 가지 주제만 읽히게 하고, 표정·그림자·윤곽선 규칙을 통일한다.

| 저장 ID 유지 | 배경 | 그림 주제 예시 |
|---|---|---|
| `purple` | 밤 보라 `#21005D` | 달을 안은 작은 캐릭터 |
| `violet` | 제비꽃 `#7223D8` | 별을 든 캐릭터 |
| `lavender` | 연보라 `#A98BE0` | 잠든 캐릭터 |
| `green` | 잎 초록 `#5E8C6A` | 새싹을 든 캐릭터 |
| `blue` | 하늘 파랑 `#5B7FA6` | 구름을 안은 캐릭터 |
| `orange` | 노을 주황 `#D9825B` | 햇살을 든 캐릭터 |
| `brown` | 코코아 `#8A6A57` | 일기장을 읽는 캐릭터 |
| `pink` | 꽃 분홍 `#C0698A` | 작은 하트를 든 캐릭터 |

그림 규격: 같은 1:1 캔버스, 얼굴/주제의 주요 부분을 원 중앙 70% 안에 배치, 원형 마스크 밖으로 중요한 요소가 잘리지 않게 한다. 50pt 설정 카드·60pt 선택 버튼·104pt 미리보기에서 알아볼 수 있는 실루엣을 우선한다. 선택 상태는 색만으로 알리지 말고 현재처럼 테두리·접근성 선택 상태를 유지한다. 원본은 편집 가능한 벡터로 보관하고, 앱에는 검토한 파일만 넣는다. 픽셀 그림으로 확정하면 @1x/@2x/@3x를 함께 수출한다.

## 사진 업로드 구현 메모

- 선택: iOS `PhotosPicker`에서 이미지 1장만 고른다. 선택을 취소하거나 iCloud 사진을 읽지 못한 경우 기존 선택은 그대로 둔다. Apple은 `PhotosPickerItem.loadTransferable`에서 iCloud 다운로드 실패가 가능하다고 설명한다([Apple PhotosPickerItem](https://developer.apple.com/documentation/photosui/photospickeritem)).
- 처리: 업로드 전에 정사각형 미리보기를 만들고 크기·품질을 제한한다. JPEG 재인코딩으로 위치 등 사진 메타데이터를 보내지 않도록 한다. 원본 업로드 여부나 자르기 UI는 화면 시안을 보고 결정한다.
- 저장: 로그인한 사용자의 UID 아래, 기존 일기 사진과 같은 최상위 폴더에 **고유 파일명**으로 새 파일을 올린다. 현재 탈퇴 정리 코드는 `{uid}/`의 바로 아래 파일을 열거하므로 중첩 폴더를 쓰면 정리 코드도 함께 수정해야 한다. Firebase는 데이터 업로드 후 `downloadURL`을 받아 프로필에 연결하는 흐름을 지원한다([Firebase Storage iOS](https://firebase.google.com/docs/storage/ios/upload-files), [Firebase Auth 프로필](https://firebase.google.com/docs/auth/ios/manage-users)).
- 프로필 값: 지금 `photoURL`은 `harudiary-avatar://…` 선택 ID다. 사진 URL을 여기에 함께 넣는다면 `프로필 이미지 = 기본 아바타 ID | 업로드 사진 URL`을 읽는 한 가지 모델을 만들고, Google/Apple 제공 사진 URL을 사용자가 올린 사진으로 잘못 취급하지 않도록 구분한다. 원격 사진 URL에 접근 토큰이 들어갈 수 있으므로 로그·분석 이벤트에 남기지 않는다.
- 교체·실패: **새 사진 업로드 → Auth 프로필 변경 → 예전 사용자 사진 삭제** 순서로 진행한다. 업로드 또는 Auth 변경이 실패하면 화면 상태는 이전 값을 유지하고, 새로 생긴 고아 파일을 정리한다. 기본 아바타로 돌아갈 때도 Auth 변경이 성공한 뒤에만 이전 업로드 파일을 삭제한다. 다른 기기에서 동시에 바꾸거나 저장 중 로그아웃한 경우에는 UID 확인과 늦은 응답 차단이 필요하다.
- 접근·삭제: Storage 규칙이 `request.auth.uid`와 경로 UID를 비교하고 파일 형식·크기를 제한하는지 확인한다([Firebase 사용자별 Storage 규칙](https://firebase.google.com/docs/storage/security/rules-conditions)). 탈퇴 테스트에서 업로드한 프로필 사진도 지워지는지 확인한다. 운영 Firebase에는 테스트 파일을 쓰지 않는다.

현재 저장소에는 Storage 보안 규칙 파일이 없으므로, 규칙의 실제 상태는 코드만으로 확인할 수 없다. `docs/SAVE_RELIABILITY.md`에는 2026-09-28 Blaze 전환 후 일기 사진 업로드 성공이 기록돼 있지만, **프로필 사진의 권한·저장·재시작 후 표시를 검증했다는 의미는 아니다.**

## 적용·검증 순서

1. 설정 목업과 현재 50pt 카드에서 단색 아이콘·Moods·자체 제작 시안 중 하나를 고른다. 임의로 여러 그림 체계를 섞지 않는다.
2. 기존 저장 ID와 이전 로컬 ID의 읽기 호환을 테스트로 고정한다. `photoURL`에 낯선 주소가 있어도 기본 표시가 유지되도록 한다.
3. 앨범 사진/기본 아바타를 한 모델로 다루고, **고유 파일 업로드 → 프로필 변경 → 이전 파일 정리** 순서를 작은 저장 책임에 모은다. 기존 일기 사진 필드와 문서 ID는 건드리지 않는다.
4. 선택된 에셋만 앱 자산에 추가하고 `ProfileAvatarView`가 저장 ID를 그림에 연결하게 한다. 닉네임·로그인 제공자 표시는 유지한다.
5. 로직 테스트와 앱 빌드를 실행한다. 실제 테스트 계정에서는 기본 아바타와 사진 각각 선택 → 저장 → 앱 종료/재시작 → 재로그인 → 다른 기기 표시를 확인한다. 업로드 실패·Auth 저장 실패·취소·계정 전환·프로필 사진 교체·탈퇴 후 파일 삭제도 확인한다.
