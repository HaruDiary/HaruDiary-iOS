# 일기 작성·수정 저장 경계

PR #4의 일기 목록 전환 뒤, 기존 `WriteDiaryVC`의 입력·사진 선택·화면 탐색은 유지하고
인증 → 이미지 정리/업로드 → 문서 저장의 순서와 결과를 `DiarySaveCoordinator`로 옮겼다.
`SceneDelegate`에서 만든 `AppDependencies.diarySaving`을 탭별 UIKit factory가 모든
작성 화면에 전달한다. 상세에서 수정으로 바뀌거나 설정→휴지통에서 편집해도 같은 경계를 사용한다.

## 보존한 계약

- 작성은 현재 계정이 없을 때 익명으로 로그인하고 `users/{uid}/diaries/{새 id}`에
  기록한다. 기존 `DiaryManager`의 날씨 조회·오늘 외 날짜 기본값·문서 ID 기록을 유지한다.
- 사진은 JPEG 품질 0.4로 업로드하며 기존 `captureTime`, `location`,
  `assetIdentifier` metadata와 사용자 UID 하위 경로를 유지한다. 여러 사진의
  완료 순서가 달라도 일기에는 선택 순서대로 성공한 URL만 기록한다.
- 수정은 열었던 계정이 여전히 로그인했는지 확인한 뒤 기존 사진 삭제, 새 사진 업로드,
  같은 문서 ID의 전체 문서 저장 순서로 수행한다. 새 사진이 없으면 `imageURL`은 `nil`이다.
  기존 항목을 복사해 수정하므로 사용자 ID, 날씨 설명, 휴지통 상태 등 편집하지 않은 필드는 보존한다.
- 기존과 같이 일부 사진 업로드 실패나 기존 사진 삭제 실패만으로 저장을 중단하지 않는다.
  인증·문서 저장 실패는 한 번의 실패 결과로 화면에 전달하고 업로드 표시를 끝낸다.
- 저장 중 중복 제출은 기존 UI 플래그로 막는다. 화면을 먼저 닫는 동작은 유지하되
  저장 실패 안내는 화면에 없는 임시 목록 대신 저장 요청 당시의 presenter에 띄운다.

## 검증과 남은 범위

`DiarySaveCoordinatorTests` 7개는 사진 없는 작성, 역순 사진 완료, 인증·문서 저장 실패,
기존 사진 삭제 후 같은 문서 ID로 수정, 사진 일부 실패, 로그아웃·계정 전환을 fake로 검증한다.
`bash scripts/ci.sh test`는 총 73개를 통과하고 `bash scripts/ci.sh build`로 앱을 컴파일한다.
CI 빌드는 가짜 Firebase 설정을 사용하며 **실행하지 않는다**.

별도로 로컬 설정 파일을 변경·복사하지 않고 시뮬레이터 앱에 참조해 실행했다.
검증용 일회성 진입 코드로 기존 목록의 `openEditor` 경로를 호출해 새 작성 화면과
가상 기존 항목의 수정 화면(기존 제목·내용, 저장 버튼)이 나타나는 것을 캡처했다.
이 일회성 코드와 프로젝트의 설정 파일 절대 경로는 검증 후 제거했다.
실제 화면 버튼 탭, Firebase 계정의 쓰기·Storage 사진 업로드, 실기기 동작은
이번 화면/오프라인 검증으로 증명되지 않는다. 기존 Storage `HTTP 400` 업로드 오류의 원인 해결,
사진 일부 실패/기존 사진 선삭제 정책 변경, 작성 초안과 입력 검증의 별도 상태 분리,
SwiftUI 작성 화면은 후속 범위다. 저장 필드명이나 서버 마이그레이션은 변경하지 않았다.
