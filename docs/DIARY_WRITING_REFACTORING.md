# 일기 작성·수정 저장 경계

PR #4의 일기 목록 전환 뒤, 기존 `WriteDiaryVC`의 입력·사진 선택·화면 탐색은 유지하고
인증 → 이미지 정리/업로드 → 문서 저장의 순서와 결과를 `DiarySaveCoordinator`로 옮겼다.
`SceneDelegate`에서 만든 `AppDependencies.diarySaving`을 탭별 UIKit factory가 모든
작성 화면에 전달한다. 상세에서 수정으로 바뀌거나 설정→휴지통에서 편집해도 같은 경계를 사용한다.

## 보존한 계약

- 작성은 현재 계정이 없을 때 익명으로 로그인하고 `users/{uid}/diaries/{새 id}`에
  기록한다. 기존 `DiaryManager`의 날씨 조회·오늘 외 날짜 기본값·문서 ID 기록을 유지한다.
- 사진은 JPEG 품질 0.4로 업로드하며 기존 `captureTime`, `location`,
  `assetIdentifier` metadata와 사용자 UID 하위 경로를 유지한다. 여러 사진의
  완료 순서가 달라도 일기에는 선택 순서대로 성공한 URL만 기록한다.
- 수정은 열었던 계정이 여전히 로그인했는지 확인한 뒤 새 사진을 업로드하고, 같은 문서 ID를 저장한 다음 이전 사진을 삭제한다. 새 사진이 없으면 `imageURL`은 `nil`이다.
  사진 업로드나 JPEG 변환이 실패하면 새 파일만 지우고 기존 사진 URL을 유지한 채 글 변경은 저장한다.
  저장된 사진을 아직 다 받지 못했거나(불러오는 중) 하나라도 받지 못한 상태에서 수정하면, 화면에 없는 사진이 지워지지 않도록
  사진은 건드리지 않고 글만 저장한다(`updateKeepingPhotos`, `ExistingPhotoLoad`). 받지 못한 사진이 있어도 로딩 표시는 끝난다.
  기존 항목을 복사해 수정하므로 사용자 ID, 날씨 설명, 휴지통 상태 등 편집하지 않은 필드는 보존한다.
- 글 저장이 실패하면 방금 올린 사진을 지운다. 빠진 사진이 있으면 성공으로 숨기지 않고 개수를 알린다.
  인증·문서 저장 실패는 한 번의 실패 결과로 화면에 전달하고 업로드 표시를 끝낸다.
- 저장 중 중복 제출은 기존 UI 플래그로 막는다. 화면을 먼저 닫고, 사진 JPEG 변환은 그 다음 백그라운드에서 한다.
  저장 실패 안내는 완료 시점의 최상위 화면에 띄운다.

## 검증과 남은 범위

`DiarySaveCoordinatorTests`는 사진 없는 작성, 역순 사진 완료, 인증·문서 저장 실패,
같은 문서 ID로 수정, 사진 일부 실패 시 글 유지, JPEG 변환 실패, 로그아웃·계정 전환을 fake로 검증한다.
통과 개수는 `docs/TESTING.md`를 따른다. `bash scripts/ci.sh build`로 앱을 컴파일한다.
CI 빌드는 가짜 Firebase 설정을 사용하며 **실행하지 않는다**.

별도로 로컬 설정 파일을 변경·복사하지 않고 시뮬레이터 앱에 참조해 실행했다.
검증용 일회성 진입 코드로 기존 목록의 `openEditor` 경로를 호출해 새 작성 화면과
가상 기존 항목의 수정 화면(기존 제목·내용, 저장 버튼)이 나타나는 것을 캡처했다.
이 일회성 코드와 프로젝트의 설정 파일 절대 경로는 검증 후 제거했다.
실제 화면 버튼 탭, Firebase 계정의 쓰기·Storage 사진 업로드, 실기기 동작은
이번 화면/오프라인 검증으로 증명되지 않는다. 기존 Storage `HTTP 400` 업로드 오류의 원인 해결,
사진 일부 실패/기존 사진 선삭제 정책 변경, 작성 초안과 입력 검증의 별도 상태 분리,
SwiftUI 작성 화면은 후속 범위다. 저장 필드명이나 서버 마이그레이션은 변경하지 않았다.

## SwiftUI 작성·수정·읽기 화면

`WriteDiaryVC`를 `Features/DiaryEditor`의 SwiftUI 화면으로 교체했다(목업 03·04·06~10·28).
편집기는 `AppShell`이 여는 시트(`DiaryEditorScreen`)다. 저장 흐름은 위의 `DiarySaving` 경계를 그대로 쓴다.

- `DiaryEditorViewModel`이 초안·사진·날씨·위치·저장을 맡는다. 화면은 표시와 입력만 한다.
  저장은 편집기가 닫힌 뒤에도 뷰모델이 끝까지 진행하고, 결과는 편집기를 연 화면에 알린다. `DiaryWriteRetention` 전역 보관은 더 쓰지 않는다.
- 날짜는 "날짜 변경" 버튼이 있는 카드로 보이고, 누르면 달력 시트가 열린다. 오늘 이후 날짜는 고를 수 없다.
  캘린더 탭(과 그날의 일기 목록)에서 쓰기 버튼을 누르면 캘린더에서 고른 날짜로 열린다. 시각은 지금 시각을 쓴다.
  고른 날이 오늘이거나 오늘 이후면 지금으로 연다. 열린 날짜만으로는 "작성 중"으로 보지 않아 닫을 때 묻지 않는다.
  감정·날씨는 이름이 붙은 격자 시트에서 고른다. 저장 값(asset 이름)과 순서는 이전과 같다.
- 날씨는 새 일기를 오늘 날짜로 쓸 때만 보여 준다. Apple 날씨 표기와 법적 고지 링크를 함께 둔다.
  편집기가 받은 날씨를 그대로 저장한다. 아직 받는 중일 때만 저장 단계에서 다시 조회한다(`DiaryWeatherStamp`).
  오늘이 아니거나 조회에 실패하면 이전처럼 `"Unknown"`/`0`을 저장한다.
- 사진은 SwiftUI `PhotosPicker`(최대 3장, 선택 순서, 기존 선택 표시)로 고른다. 번호·삭제·크게 보기를 제공한다.
  크게 본 사진은 닫기 버튼을 누르거나 아래로 끌어 내리면 닫힌다. 끄는 동안 사진이 줄어들며 일기가 비쳐 보이고,
  충분히 끌고 놓으면 그 자리에서 줄어들며 사라진다. 확대한 사진과 옆으로 넘기는 동작에는 반응하지 않는다.
  읽지 못한 사진(예: iCloud에서 내려받지 않은 사진)은 넣지 않고 몇 장을 못 넣었는지 알린다.
  사진 보관함 접근을 거부해도 사진을 고를 수 있다(촬영 정보는 파일에서 읽는다).
  저장소 metadata 형식은 이전과 같다. 사진 보관함 접근이 제한되어 있어 촬영 시각·위치를 보관함에서 못 읽으면
  사진 파일의 EXIF에서 읽고, 그래도 없으면 metadata 없이 사진을 넣는다. 이전에는 이 경우 사진이 조용히 빠졌다.
- 사진을 불러오는 동안에는 스피너 대신 사진 자리에 빛이 지나가는 스켈레톤(`PhotoSkeleton`)을 보여 준다.
  사진은 도착하면 서서히 나타난다. 목록·캘린더·휴지통 썸네일, 작성 화면 사진 줄, 읽기 화면 사진이 같은 방식이다.
- 지도는 보여 주지 않는다. 위치가 있는 사진을 처음 넣으면 "사진의 위치를 넣을까요?"를 묻는다.
  넣으면 `useMetadataLocation`을 켜고 장소 이름을 한 줄로 보여 준다(작성 화면에서는 뺄 수 있다). 날짜는 바꾸지 않는다.
  새 일기를 쓴 곳(`currentLocationInfo`)은 이전처럼 저장하지만 화면에는 보이지 않는다.
- 수정 저장 규칙:
  - 바뀐 것이 없으면 아무것도 쓰지 않고 닫는다. 읽기 화면의 연필과 저장 버튼이 같은 자리여서, 연필을 두 번 누르면 바로 저장되던 문제를 막는다.
  - 사진을 건드리지 않았으면 기존 사진 URL을 그대로 둔다. 다시 압축·업로드하지 않으며, assetIdentifier가 없는 옛 사진도 그대로 남는다.
  - 사진을 바꾸면 남은 기존 사진은 파일·URL을 그대로 두고 새 사진만 올린다(`DiaryPhotoSlot`, `update(photos:)`).
    지운 기존 사진 파일은 저장 뒤에 삭제한다. 새 사진 업로드가 하나라도 실패하면 새 업로드만 지우고 기존 사진을 유지한 채 글을 저장한다.
    assetIdentifier가 없는 옛 사진이 있어도 사진 변경이 저장된다.
  - 저장된 사진을 불러오는 중에는 사진 선택기를 열지 않는다. 새로 고른 사진을 불러오는 중에는 저장하지 않는다.
- 새 일기만 현재 위치를 기록한다. 이전에는 기존 일기를 수정할 때도 저장된 위치를 지금 위치로 덮어썼다.

`DiaryEditorViewModelTests`는 fake 저장소·사진·날씨·위치로 위 규칙을 검증한다.
시뮬레이터에서는 작성·날짜/감정/날씨 시트·닫기 확인·읽기·사진 보기·수정 화면을 확인했다.
실제 새 일기 저장과 실기기 동작은 확인하지 않았다.
기존 UIKit 편집기 파일과 `DiaryPhotoReplacement`는 삭제했다([안 쓰는 코드 정리](LEGACY_CLEANUP.md)).

## 쓰던 글 보관과 글감 질문

- 새 일기를 쓰는 동안 제목·내용·날짜·감정·날씨를 기기에 보관한다(`DiaryDraftStoring`, `UserDefaultsDiaryDraftStore`, 키 `diaryDraft.v1`).
  서버에는 아무것도 쓰지 않고, 저장 스키마도 그대로다.
  - 앱이 꺼지거나 저장에 실패해도 글이 남는다. 다음에 일기 쓰기를 열면 그 글이 그 날짜로 돌아오고 "쓰던 글을 불러왔어요"를 알린다.
    캘린더에서 다른 날짜를 골라 열어도 보관된 글과 그 날짜가 우선이다.
  - 사진은 보관하지 않는다. 몇 장이었는지만 보관해 다시 넣으라고 알린다.
  - 편집기는 저장을 시작하면 닫히므로, 저장이 도는 동안 다른 편집기가 열릴 수 있다. 그래서 보관소는 앱 전체에 하나이고
    (`AppDependencies.diaryDrafts`), 저장 중인 글을 알고 있다. 저장 중인 글은 새 편집기에 다시 불러오지 않고, 저장이 끝나면
    그 저장이 시작할 때 보관돼 있던 글만 지운다(그 사이 새로 쓴 글은 남는다). 저장을 시작한 편집기는 그 뒤로 아무것도 보관하지 않는다.
    저장 중이라는 표시는 앱이 켜져 있는 동안만 유효하다. 저장 도중 앱이 꺼지면 글은 보관된 채 남아 다음에 돌아온다.
  - 저장에 성공하거나 "작성을 그만할까요?"에서 나가기를 누르면 지운다. 글을 다 지워도 지운다.
  - 다른 계정이 쓰던 글은 보여 주지 않는다. 편집기를 여는 것만으로는 지우지 않아, 그 계정이 다시 로그인하면 돌아온다.
    새 일기의 글은 한 번에 하나만 보관하므로, 지금 계정이 글을 쓰기 시작하면 그 글이 자리를 대신한다.
    계정이 없을 때 쓴 글은 이어 쓰는 사람의 것으로 본다.
  - 글의 주인은 쓰기를 시작한 계정으로 고정한다. 편집기가 열린 채 로그아웃되거나 다른 계정으로 바뀌면 그 뒤로는 보관하지 않고,
    이미 보관된 글은 원래 주인의 것으로 그대로 둔다. 계정 없이 시작한 글은 그 뒤에 생긴 계정(저장 때 만드는 익명 계정)의 것이 된다.
- 저장된 일기를 고치는 동안에도 고친 제목·내용·날짜·감정·날씨를 기기에 보관한다(키 `diaryDraft.edit.v1`, 새 일기의 글과 따로).
  - 가장 최근에 고치던 일기 하나만 보관한다. 그 일기를 다시 수정으로 열면(읽기 화면의 연필 포함) 고친 내용이 돌아오고
    "고치던 내용을 불러왔어요"를 알린다. 읽기 화면은 저장된 그대로 보여 준다.
  - 사진 변경은 보관하지 않는다. 새로 넣던 사진이 몇 장이었는지만 알려 준다.
  - 수정 저장에 성공하거나 "나가기"를 누르거나 원래대로 되돌리면 지운다. 저장에 실패하면 남는다.
  - 고치던 계정과 같은 계정에서만 돌아온다.
- 새 일기 화면의 제목 아래에 글감 질문을 한 줄 보여 준다(`DiaryPrompts`, 30개). 같은 날에는 같은 질문이고, 옆의 버튼으로 다음 질문을 본다.
  질문은 보여 주기만 하고 일기에 저장하지 않는다.
