# HaruDiary 리팩토링 로드맵

## 방향

**기존 구성요소 분류와 최소 공통 기반을 먼저 준비하고, 동작 테스트 → 로직 분리 → SwiftUI 화면 교체 순서로 진행한다.**

약 한 달을 기준으로 한 큰 그림이다. 담당자와 세부 작업 배분은 아직 정하지 않는다.
기존 Firebase 계정·일기·사진과 저장 형식은 유지한다. 마을 기능의 상세 기획과 구현 계획은
추후 논의한 뒤 별도 추가한다. 이번 로드맵에서 보상 규칙이나 데이터 구조를 확정하지 않는다.

## 전체 순서

```text
UIKit 구성요소·의존성 분류
        ↓
공통 기반 정리·현재 동작 테스트
        ↓
모델·날짜 처리 정리
        ↓
Firebase·외부 서비스 접근 분리
        ↓
작성·조회·수정·삭제 로직 분리
        ↓
화면 상태와 비즈니스 로직 분리
        ↓
목업 기반 SwiftUI 전환
        ↓
통합 검증
```

## 0. 전환 현황과 공통 기반 먼저 준비

[UIKit → SwiftUI 전환 준비](UIKIT_SWIFTUI_MIGRATION.md)에 현재 코드의 분류와 전환 방향을 정리했다.

- 재사용할 모델·SDK·자산, 분리할 서비스, 교체할 화면·레이아웃, 정리 후보를 구분한다.
- 기존 색상 자산을 기준으로 공통 색상·타이포·여백 규칙을 먼저 합의한다.
- 날짜·설정·오류·공통 함수의 책임과 위치를 정한다. 실제로 필요한 최소 구현부터 만든다.
- 사진 선택/메타데이터·키보드·인증 등 UIKit 의존 기능의 동등성 검증 항목을 적는다.
- 버튼·카드 등 완성 컴포넌트와 앱 화면은 이후 실제 사용처와 함께 구현한다.

**완료 기준:** 무엇을 유지/교체할지와 공통 기준이 명확해 두 사람과 AI가 같은 기반에서 시작할 수 있다.

## 1. 현재 동작과 데이터 계약 고정

**무엇부터:** `EveryDiary/EveryDiary/Model/DataModel.swift`

- 기존 일기 필드, 날짜 문자열, 사진 배열, 삭제 상태의 정상/오류 사례를 정리한다.
- 현재 동작을 테스트로 기록하고, 보존할 동작과 수정할 버그를 구분한다.
- 저장 모델과 UIKit 사진/설정 셀 모델, 날짜 formatter의 책임을 분리한다.
- 저장 필드명과 기존 날짜 offset을 유지한다. 잘못된 날짜를 오늘로 처리하는 동작은
  별도 기대값을 정한 후 수정한다.

**완료 기준:** 기존 데이터가 같은 의미로 읽히고 저장되며, 변경 영향을 테스트로 확인할 수 있다.

## 2. 데이터 접근과 외부 서비스 분리

**대상:** `RemoteDB/FireStore.swift`, `PaginationManager.swift`,
`FirebaseStorageManager.swift`, `Service/WeatherService.swift`

- 먼저 일기 조회를 Repository 인터페이스 뒤로 옮기고, 저장·수정·삭제를 순차적으로 옮긴다.
- Firebase 구현과 앱이 사용하는 계약을 구분한다. 테스트에서는 fake 저장소를 사용한다.
- 이미지·날씨·인증의 외부 의존성을 필요한 경계에서 분리한다.
- pagination의 다음 페이지, 종료, 오류/재시도와 listener 해제 책임을 명시한다.
- 새 경계를 기존 UIKit 코드에 연결한다. 사용하지 않는 추상화만 만들지 않는다.

**완료 기준:** UI가 Firebase 쿼리를 직접 조합하지 않고, 운영 서버 없이 주요 로직을 테스트할 수 있다.

## 3. 사용자 동작별 로직 분리

**대상:** `WriteDiary/DiaryUploadManager.swift`, `WriteDiaryVC.swift`,
`RemoteDB/FireStore.swift`와 해당 호출부

- 작성·수정·조회·검색·휴지통 이동·복원을 각각의 책임으로 정리한다.
- 사진 업로드와 일기 저장의 순서, 일부 실패, 중복 저장, 취소를 명확히 한다.
- 삭제·복원과 이미지 정리가 어긋나지 않도록 실패 경로를 테스트한다.
- 익명/기존 로그인 상태, 재진입, 구독 해제 등 현재 기능의 수명을 정리한다.
- 폴더 이동이나 파일 길이 축소보다 책임 분리와 동작 검증을 우선한다.

**완료 기준:** 기존 UIKit 화면에서도 새 로직을 통해 같은 기능이 동작한다.

## 4. 화면 상태 분리

**대상:** 일기 목록·작성·캘린더 등 기존 ViewController의 상태 처리

- 로딩·내용·빈 상태·오류·재시도와 작성 초안을 화면 코드에서 분리한다.
- 입력 검증, 저장 가능 여부, 저장 실패 후 초안 보존을 UI 없이 테스트한다.
- UI 갱신의 main actor 경계와 비동기 작업 취소·listener 해제 책임을 명시한다.
- 이후 SwiftUI가 같은 상태·로직을 사용할 수 있게 만든다.

**완료 기준:** 화면을 교체해도 데이터 조회·저장과 상태 처리 로직을 다시 작성할 필요가 없다.

## 5. 마지막으로 SwiftUI 전환

**대상:** `TabBarController.swift`, `SceneDelegate.swift` 및 기존 화면들

- 앞서 합의한 색상·타이포·여백을 사용하고, 반복 UI 컴포넌트를 첫 사용처와 함께 구현한다.
- 목록/상세처럼 읽기 중심 화면 → 작성/수정 → 캘린더/설정 → 앱 진입과 탐색 순으로 전환한다.
- 새 뷰는 이미 검증된 상태 모델과 Repository를 사용한다.
- 기존 기능(사진·감정·날씨·검색·휴지통·인증·알림·잠금·온보딩)을 빠뜨리지 않는다.
- 여정 영역의 새 마을 디자인/기능은 별도 논의 후 계획에 추가한다.
- 전환이 끝난 UIKit 코드만 제거한다. SwiftUI PR에 새로운 저장 정책을 섞지 않는다.

**완료 기준:** 기존 기록을 유지하며 목업 기반 SwiftUI 화면에서 주요 사용자 흐름을 사용할 수 있다.

## 한 달의 대략적인 배치

| 기간 | 중심 작업 | 확인할 결과 |
|---|---|---|
| 1주 차 | 전환 목록·공통 기반, 동작 테스트, 모델·날짜 정리 | 재사용/교체 기준과 기존 데이터 계약이 명확함 |
| 2주 차 | Repository·서비스 경계, 사용자 동작 로직 분리 | fake로 테스트하고 기존 UIKit에도 연결됨 |
| 3주 차 | 남은 로직 정리, 화면 상태 분리, 실패 경로 검증 | SwiftUI 전환 전 로직 완료 기준 충족 |
| 4주 차 | SwiftUI 화면 교체와 통합 검증 | 전환된 화면의 데이터 호환·실사용 검증 |

일정은 예상이며, 상세 화면 범위와 두 사람의 가용 시간에 따라 조정한다.
마지막 주에 모든 화면 전환과 검증이 가능한지는 2주 차 말에 다시 판단한다.
일정이 부족하면 범위/기간을 함께 조정하며, 테스트나 데이터 보존을 생략하지 않는다.
새 마을 기획은 이 일정에 포함해 완료한다고 가정하지 않는다.

## SwiftUI를 시작하기 전 확인

- [ ] 재사용/교체 목록과 공통 색상·타이포·여백 기준이 있다.
- [ ] 기존 저장 필드·계정·일기·사진의 호환성이 유지된다.
- [ ] 새 Repository와 사용자 동작 로직을 기존 앱이 실제로 사용한다.
- [ ] 작성·조회·수정·삭제/복원과 주요 실패 경로의 테스트가 통과한다.
- [ ] 화면 상태가 ViewController 또는 Firebase 구현에 직접 묶여 있지 않다.
- [ ] 목업 전환 범위와 우선순위를 함께 확인했다.

## 협업의 최소 기준

- 담당은 착수 전에 정한다. 여기서는 특정 사람에게 영역을 배정하지 않는다.
- 같은 모델·프로젝트 파일을 동시에 크게 수정하지 않도록 작업 범위를 공유한다.
- 테스트 → 책임 분리 → 호출부 연결 단위로 작은 PR을 만든다.
- 두 사람 모두 같은 `AGENTS.md`와 컨벤션을 AI에 읽힌다.
- 각 단계는 테스트와 실제 사용 증거를 남기고 다음 단계로 넘어간다.

## 현재 준비된 것과 다음 시작점

현재 추가한 것은 PR 템플릿, 컨벤션, AI 공통 지침, 모델 회귀 테스트 6개와 CI다.
위 리팩토링 자체는 아직 시작하지 않았다.

**먼저 전환 목록을 함께 검토하고 공통 기반의 최소 범위를 정한다.**

그 다음 `FireStore.swift`의 조회 책임부터 Repository로 옮긴다.
